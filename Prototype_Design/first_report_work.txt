1.1 Fact-finding Techniques
Our requirement discovery combined four techniques and then triangulated results before freezing Sprint 1 scope.

Interviewing (MO and Admin): We conducted semi-structured interviews with Module Organisers and admin users to identify decision points, required fields, and status-transition pain points. Findings mapped directly to P0-005 (post position), P0-006 (view applicants), and P0-007 (review decision).

Questionnaires (TA applicants): We collected short structured responses on profile setup, position search, application action, and feedback visibility. This validated P0-001 to P0-004 and P0-013 as core candidate-side needs.

Document analysis: We reviewed the existing form-and-Excel process, template constraints, and project handout constraints. This defined mandatory entities and rules: profile data completeness, position deadline, one-application-per-position validation, and role-based access.

Observation of current workflow: We observed manual recruitment updates and identified delay and inconsistency risks. This drove dashboard-first visibility in prototypes and explicit status labels for both TA and MO views.

Evidence traceability from findings to outputs:
- Product backlog evidence: Product_Backlog.xlsx contains 50 stories in total, including 49 stories with clear priority and sprint mapping (P0/P1/P2/P3 across Iteration 1/2/3/4) and 1 technical item marked uncertain.
- Prototype evidence for first assessment: login.html, ta_dashboard.html, ta_profile.html, ta_positions.html, mo_dashboard.html, mo_post_position.html, mo_applicants.html, admin_dashboard.html.

1.2 Iteration Plan
Our plan follows Agile incremental delivery with four iterations aligned to backlog sprint numbers.

Iteration 1 (Sprint 1, completed in current assessment scope):
- Deliverables: Product backlog baseline, medium-fidelity prototype pages, and first brief report.
- Story scope: Priority P0 stories (12 items) focusing on end-to-end minimum flow.
- Covered flow: TA profile + application + status visibility, MO posting + review, role login and baseline error handling.

Iteration 2 (Sprint 2, planned):
- Story scope: Priority P1 stories (13 items) for efficiency and usability.
- Main targets: profile editing, filtering, resume-path upload, batch review support, pagination, operation logs, admin account management.
- Engineering target: move from prototype interaction to stable executable logic while preserving file-based persistence constraints.

Iteration 3 (Sprint 3, planned):
- Story scope: Priority P2 stories (16 items) for enhancement functions.
- Main targets: favorites, reminders, export functions, skill requirements, auto close by deadline, workload warning, data backup/recovery, bilingual UI.

Iteration 4 (Sprint 4, planned):
- Story scope: Priority P3 stories (8 items) for explainable AI-assisted support and human override.
- Main targets: matching score, skills-gap suggestions, AI-assisted ranking/statistics, configurable weights, and manual verification of AI outputs.
- Exit criteria: integration hardening, regression testing, and final acceptance readiness.

1.3 Prioritisation Methods
We applied MoSCoW as the primary method and adjusted by three factors: business value, implementation dependency, and delivery risk. Priorities are recorded in Product_Backlog.xlsx.

Must Have (P0, 12 stories):
- Required for a complete TA-MO-Admin minimum flow.
- Typical examples: P0-001 profile creation, P0-003 application submission with duplicate check, P0-005 position posting, P0-007 review decision, P0-009 role-based login, P0-011 error handling.

Should Have (P1, 13 stories):
- Improves efficiency after core flow is stable.
- Typical examples: P1-002 filtering, P1-003 resume upload path, P1-007 batch review, P1-011 pagination, P1-012 operation logs.

Could Have (P2, 16 stories):
- Adds useful but non-blocking product value.
- Typical examples: P2-001 favorites, P2-002 local reminders, P2-006 auto close by deadline, P2-008 workload threshold warning, P2-012 backup/recovery.

Future Advanced (P3, 8 stories):
- AI-assisted capabilities with explainability and human override.
- Typical examples: P3-001 matching score, P3-004 resume keyword extraction, P3-007 configurable weights, P3-008 manual verification.

How prioritisation controlled sprint scope:
- Sprint 1 delivered only P0 baseline.
- Sprint 2/3/4 are mapped to P1/P2/P3 respectively, reducing scope creep and preserving delivery feasibility.

1.4 Estimation Methods
Current backlog evidence shows estimation is managed by two linked dimensions:
- Relative scope ordering through Priority + Iteration assignment.
- Delivery window control through sprint capacity.

Fields in Product_Backlog.xlsx:
- Estimation/day column exists and is reserved for time estimates.
- In the current baseline version, this column is not filled yet; therefore this report uses a method statement (not fabricated numeric durations) for consistency with source data.

Estimation method used by the team:
1) Start from acceptance criteria, not only story title.
2) Break each story into UI, validation, business rule, persistence, and verification tasks.
3) Evaluate risk multipliers: cross-role coupling, status transition complexity, and file-based persistence impact.
4) Place stories into sprint by capacity and dependency order.
5) Re-estimate when scope, rule, or dependency changes.

Operational estimation rule for upcoming software iterations:
- Small: isolated UI update with no cross-role data impact.
- Medium: single-role CRUD with validation and local persistence.
- Large: cross-role status synchronization or permission-sensitive workflow.
- Extra-large: AI-assisted or system-wide analytics features requiring explainability and override.

Definition of Done for estimation closure:
- Acceptance criteria satisfied.
- Negative cases covered (e.g., empty input, duplicate apply, expired position, invalid login).
- Role-to-role state consistency demonstrable on prototype/software flow.
- Output is reviewable in sprint demo.
